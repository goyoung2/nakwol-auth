# NAKWOL AUTH v0.2.0 Formal Release Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Promote the verified AUTH v0.2.0 candidate through `dev -> main -> stable`, verify the resulting production deployment, and create the immutable `auth-v0.2.0` GitHub component release from the exact verified stable target.

**Architecture:** No feature expansion is allowed in this release pass. The only runtime delta awaiting promotion is the V8-A refactor/test that extracts the already-existing Discord callback refresh sequence into `refreshDiscordMembership()` and proves membership-policy refresh behavior. Formal release creation remains fail-closed through the existing `release/* -> stable` provenance guard and `ops/release.json` descriptor.

**Tech Stack:** GitHub pull requests/actions, Cloudflare Workers, TypeScript, Node test runner, Wrangler, D1, Cloudflare Service Binding.

**Spec:** `docs/releases/2026-08-29-nakwol-auth-v0.2.md`

## Global Constraints

- Preserve `feature/fix/chore/docs -> dev -> main -> stable -> component release` promotion order.
- Use squash merges and pin every merge with the expected PR head SHA.
- Do not weaken stable-promotion provenance, repository-governance, DATA-first deployment ordering, OAuth/PKCE/state/CORS/logout guards, or immutable SDK checks.
- Do not mutate Discord guild roles for V8-B; the approved v0.2.0 waiver is authoritative until controlled role-management authority is available.
- Do not expose raw access tokens, cookies, token hashes, Discord/Cloudflare secrets or PKCE verifiers.
- Do not create `auth-v0.2.0` before the final verified stable target exists.
- `ops/release.json.target_sha` must point at the final verified stable commit, never a `dev` or `main` SHA.
- No unrelated AUTH, DATA, Connect, schema, migration, registry or SDK changes are permitted.
