# NAKWOL AUTH 상용 계획 독립 리뷰

작성일: 2026-09-30

**종합 판정: ITERATE — 추가 요구사항과 인증 경계 계약을 보완한 뒤 구현 계획을 다시 승인해야 한다.**

## 1. 검토 방법과 범위

- 기준: `561d78fe3a49cd6bbadc695dc075c3772cff2279`.
- [설계안](../superpowers/specs/2026-09-30-commercial-auth-design.md)과 [개발 계획](../superpowers/plans/2026-09-30-commercial-auth.md)을 검토했다.
- 독립 리뷰어 2명을 `fork_turns=none`으로 실행했다. 기존 대화와 작성자의 설명/결론을 전달하지 않고 대상 파일, 사용자 목적, 이번 추가 요구사항, 인덱스의 한계만 전달했다.
- `independent_product_review`: 제품 완결성, 서비스 소유자 권한, 사용자 관리, 설치·운영 경험. 판정 **ITERATE**.
- `independent_architecture_review`: 앱 간 권한 격리, 갱신 경쟁, 권한 만료, UI 설정 보안, 구현 가능성. 판정 **ITERATE**.
- 두 리뷰어는 읽기 전용으로 검토했다. 코디네이터는 핵심 지적을 현재 소스와 문서 행에 대조했다.
- 보고서 작성 후 같은 두 리뷰어가 통합 내용의 정확성을 다시 확인했다. 모두 '보고서 반영 정확, 원안 판정 ITERATE 유지'로 회신했다. 원본 개정안이 통과했다는 뜻은 아니다.
- 그래프 세대는 2026-09-27이고 docs/assets 미포함 또는 source 변경이 있어 직접 파일을 읽었다. 전체 코드 보안 감사, 운영 재배포, 신규 기능 테스트를 수행했다는 의미가 아니다.
- **원본 두 문서는 수정하지 않았다.** 아래는 후속 개정에 반영할 리뷰 결과와 수정 권고다. 제품 코드·운영 정책·외부 사이트도 변경하지 않았다.

## 2. 요구사항 커버리지

| 이번 사용자 요구 | 원래 두 문서의 상태 | 필요한 보완 |
|---|---|---|
| 자기 서비스에 접속한 사용자 조회 | 개별 ID 진단은 있지만 서비스 이용자 목록 계약 없음 | 앱-사용자 관계, 최초 승인/최근 관측, 페이지네이션, 데이터 범위 |
| 자기 서비스 사용자 관리 | 개발자를 제한된 진단으로 묶어 요구와 충돌 | 앱 차단/해제, 앱 세션 종료, 허용 범위의 예외와 감사 |
| 사이트 내 인증 UI 편집 | 상태 표현만 설명 | 표시/숨김, inline/fixed/sticky, 위치, 디자인 토큰, 미리보기 |
| 로그인 전·확인 중 화면 편집 | 고정 화면 동작만 설명 | 별도 presentation 설정과 공개 bootstrap, 안전한 편집/게시/복원 |
| 유지 시간·재검증 정책 | 값 범위는 있으나 owner 권한·흐름 불명확 | 운영자 상한 안의 서비스별 설정, 실효값·전파 상태 |
| 초기 설치의 편의성 | 호스팅/CLI 설치 중심 | UI·정책 선택과 실제 미리보기를 포함한 설치 마법사, 재개·동기화 |

사용자는 목록에서 5개 관리 요구와 초기 설치 편의를 제시했다. 모두 독립 합격 조건으로 반영해야 한다.

## 3. 통합 지적 사항

### R1 — P1: 개발자 권한 계약이 고객 요구와 충돌

**근거:** 설계272행은 개발자를 '소유 앱의 상태/제한된 진단만'으로 제한한다. 계획128~135행 및192~201행은 owner가 어떤 작업을 할 수 있는지 정의하지 않는다.

**위험:** 외부 개발자가 사용자 문제를 자체 해결할 수 없어 SDK 운영자가 모든 서비스의 고객지원을 떠맡게 된다. 화면 버튼만 추가하면서 권한을 넓히면 앱 간 영향이 생긴다.

**현재 코드 주의:** `src/access-support.ts:70-79`의 reauthenticate는 중앙 세션·모든 앱 코드·토큰을 회수한다. 현재는 AUTH 운영자 전용이므로 외부 개발자가 이미 실행 가능하다는 취약점 주장은 아니다. 여기에 owner 검사만 추가하는 수정이 위험하다는 뜻이다.

**수정:** 앱 소유자와 AUTH 운영자의 관리 API/응답/조치 scope를 분리한다. `src/connect-cli-apps.ts:69-75`의 소유 검사와 함께 target user/session/operation의 clientId도 검사한다. app별 세션 회수 API는 전역 테이블 삭제를 하지 않는다.

**필수 시험:** A owner가 B clientId/sessionId/operationId를 넣거나 global scope로 요청하면 거부. A 차단/로그아웃 뒤 B 세션 유지. 소유권 회수 뒤 기존 관리 토큰으로 변경 불가.

### R2 — P1: 서비스 사용자 목록과 '접속'의 의미가 없음

**근거:** 설계248~253행은 Discord ID/지원 코드 진단이다. 계획195행/244행에는 앱 사용자 목록을 위한 관계와 접근 관측 저장 경로가 없다.

**위험:** 중앙 로그인 이력을 실제 서비스 방문 목록으로 오인하거나, 목록을 만들려고 모든 이미지 요청을 중앙에 기록해 성능을 다시 악화시킬 수 있다.

**수정:** `인증 시도`, `앱 접근 승인`, `게이트 접근 관측`을 구분한다. 앱과 관계 없는 중앙 계정은 목록에서 제외. 비로그인 익명 요청은 Discord 사용자를 식별할 수 없으며 '누구인지'를 임의 추정하지 않는다.

**필수 시험:** 최초 승인, 로컬 lease 재방문, 거부된 인증, 미방문 중앙 사용자, 관측 업로드 장애를 구분. 오류 로그 누락이나 지연 때문에 '현재 접속 중'이라고 허위 표시하지 않는다. 관측량을 성능·비용 시험에 포함한다.

### R3 — P1: 표시 UI와 로그인·대기 화면 편집의 제품 계약 누락

**근거:** 설계117행 및227~229행, 계획T03/T09에 편집 스키마·프리뷰·게시가 없다. 현재 `src/assets/nakwol-auth-web-v0.3.2.js.txt`에는 variant/theme 토큰 기반 UI가 일부 있고, `nakwol-connect-v1.js.txt:338-359`에는 headless 지원과 고정 dark/compact 위젯 설정이 있다. 편집 기능이 완전히 없는 것이 아니라 재사용 가능한 기반과 제품화되지 않은 설정이 섞여 있다.

**수정:** 정책과 별도의 서비스별 `presentation` 스키마를 만든다. 위젯과 로그인/확인 화면을 같은 설정 버전으로 미리 보고 게시한다. 서버 보호 설정과 표시 설정을 묶지 않는다.

**필수 시험:** hidden/inline/fixed/sticky 전체에서 비로그인 자료 차단. 보호 앱 bundle 없이 로그인 화면 표시. script/HTML/위험 URL 주입 거부. 깨진 로고·설정 로딩 실패·테마 rollback에서도 로그인/재시도/지원 경로가 작동한다.

### R4 — P1: 외부 개발자에게 보이는 개인정보 범위 불명확

**근거:** 설계248~251행은 중앙 계정·세션·역할·차단 진단을 포함하지만 owner 응답 스키마가 없다. 설계270~272행의 '제한된 진단'만으로 정보 범위를 판정할 수 없다.

**수정:** 앱 owner용 DTO를 중앙 운영자용과 분리한다. 자기 앱과의 관계가 있는 사용자만 조회하고 다른 앱 활동·관련 없는 역할·중앙 내부 제재 사유는 제공하지 않는다. 사용자 삭제는 앱 관계/관측 삭제이며 중앙 계정 삭제가 아니다.

**필수 시험:** 목록/검색/상세/내보내기/조치 상태 조회의 tenant 경계, 지원 코드로 타인 정보 조회 금지, 임의 Discord ID로 중앙 가입 여부 열거 금지. 삭제 후 타 앱 데이터 보존.

### R5 — P1: refresh 회전의 경합과 응답 역전 계약 부족

**근거:** 설계217행, 계획145행은30초 idempotency와 CAS를 말하지만 isolate들이 같은 갱신을 식별하는 키 및 늦은 Set-Cookie 처리가 정해져 있지 않다.

**위험:** 정상 병렬 요청이 서로 다른 키를 만들거나, 최신 쿠키 뒤에 오래된 응답이 도착하면 정상 사용자가 토큰 재사용 공격으로 분류돼 로그아웃될 수 있다. 구현된 취약점이 아니라 계획의 미해결 동시성 문제다.

**수정 권고:** 초기 구현은 **안정적인 사이트 session handle + 중앙 서버의 refresh family 조정**으로 명세를 구체화한다. 브라우저에는 회전하는 refresh token 대신 HttpOnly handle과 로컬 승인 proof를 둔다. 중앙 갱신은 client/origin/session/generation 단위로 원자 조정한다. 늦은 proof가 덮여도 다음 재검증이 같은 서버 세션의 최신 상태로 회복하며 정상 경합만으로 family를 폐기하지 않는다. 매 이미지 중앙 handle 조회를 요구하지 않도록 기존 로컬 proof hot path를 유지한다.

이 권고는 설계 선택지이며 아직 구현/검증되지 않았다. 안정 handle 자체도 bearer credential이므로 앱/origin 바인딩, 수명·회수·키 회전은 계속 필요하다. 이미 유효한 lease의 회수 지연은 운영 프로필 상한을 따른다.

**필수 시험:** 2isolate 동시 갱신, 이전 응답30초 이상 지연, 다음 세대 발급 뒤 이전 응답 도착, 응답 유실, 갱신 중 logout/deny. 정상 경합의 강제 로그인0, 회수 이후 신규 승인의 부활0.

### R6 — P2: 승인 근거와 무관한 만료를 lease 계산에 포함

**근거:** 설계172행, 계획131행은 roleExp/grantExp를 모두 최솟값에 넣는다. 현재 `src/policy.ts:66-78`의 승인 분기는 role, manual grant, guest에 따라 요구 증거가 다르다.

**수정:** 공통 token/session/lease 상한에 **실제 승인에 사용한 증거**의 만료만 추가한다.

| 승인 근거 | 추가 만료 상한 |
|---|---|
| 역할 기반 | 사용한 역할 증거 validUntil |
| 수동 허가 | 해당 grant expiresAt, 단 grant가 면제하지 못하는 전역 조건은 계속 검사 |
| 역할 조건 없는 guest | 역할 만료를 추가하지 않음 |
| admin/lab | 해당 권한의 명시된 증거 수명; member 역할을 임의 대체 근거로 사용하지 않음 |

만료 grant가 있더라도 정상 역할로 접근 가능한 경우에는 역할 경로로 다시 평가한다. explicit deny/사용자·앱 비활성은 모든 허가보다 우선한다.

**필수 시험:** stale role+유효 플랫폼 승인 grant, 정상 role+만료 grant, guest+role 없음, grant+deny. `source`와 실제 계산 근거 일치.

### R7 — P2: 초기 설치 마법사와 설정 동기화 누락

**근거:** 설계117행, 계획92~101행/235~247행은 호스팅과 배포가 중심이다. UI·정책 편집을 처음 설치할 때 완료하는 흐름이 없다.

**수정:** 서비스 생성/선택 → 호스팅/origin → UI 프리셋과 미리보기 → 정책 선택 → 검토/저장 → 설치/배포/차단검증 단계. 비대화형 JSON과 브라우저 마법사가 같은 검증 스키마를 사용한다.

**필수 시험:** 소스·OAuth·쿠키 코드를 수작업으로 수정하지 않고 지원 플랫폼에서 설치 가능. 중단 후 재개, 앱/credential 중복 생성0, 설정 충돌409, 설치와 실제 배포의 상태 분리.

### R8 — P2: 서비스 소유자의 정책 선택과 적용 확인 부족

**근거:** 설계138~148행에 범위는 있지만272행의 owner 권한과 연결되지 않는다. 계획129~135행에는 owner가 실제로 선택하는 흐름이 없다.

**수정:** 플랫폼 안전 상한 안에서 own-app 로그인 유지 기간과 권한 재검사 간격을 변경할 수 있게 한다. '2시간 로그인 유지' 같은 요구가 access token 만료와 혼동되지 않도록 session idle/absolute와 tokenTTL을 구분한다. 현재 계획의 absolute 최소1일은 시간 단위 운영 요구에 맞게 다시 검토한다.

**필수 시험:** owner가 허용 값 변경→지원 runtime 반영 확인. 범위 밖 값·타 앱 변경 거부. 기간 축소 기한 준수, 기간 확대 후 만료 세션 부활0. 이전 runtime은 저장만 됐다고 적용완료 표시 금지.

## 4. 개정판에 넣을 최소 권한표

아래는 코디네이터가 두 리뷰의 권고를 통합한 **개정 제안**이다. 기존 권한을 실제 부여한 것이 아니다.

| 기능 | AUTH 운영자 | 해당 서비스 소유자 | 다른 서비스 소유자 |
|---|---|---|---|
| 서비스 사용자 목록/접근 기록 | 운영 목적 범위 | 자기 앱의 최소 필드 | 불가 |
| 서비스 차단/해제 | 가능 | 자기 앱만 | 불가 |
| 서비스 세션 종료/재연결 요구 | 가능 | 자기 앱만, 중앙 SSO 보존 | 불가 |
| 중앙 전체 로그아웃/global deny | 가능 | 불가 | 불가 |
| 시즌3 기준/전역 member/admin 변경 | 가능 | 불가 | 불가 |
| 임시 허가 | 감사·기한 필수 | 플랫폼이 위임한 앱 조건 범위만 | 불가 |
| 위젯/로그인 화면 디자인 | 가능 | 자기 앱만 | 불가 |
| 세션/재검사 설정 | 전역 상한·기본값 | 위임된 범위의 자기 앱 | 불가 |
| 전역 역할 freshness/credential | 가능 | 직접 접근 불가 | 불가 |
| 자기 앱 사용자 관계 삭제 | 감사와 보존 정책에 따름 | 자기 앱 기록만, 차단 해제와 별개 | 불가 |

특히 외부 개발자의 임시 허가로 시즌3 필수 조건이나 중앙 차단을 우회하면 안 된다. 중앙 운영자가 별도로 승인한 예외와 서비스 자체 제한 해제를 분리한다. guest 허용 앱인지 member 고정 앱인지도 앱의 capability로 정해 기존 소유자의 권한을 몰래 축소하거나 확대하지 않는다.

팀 관리자·지원 담당·읽기 전용 역할 위임은 유용한 확장이지만 이번 최소 기능은 **AUTH 운영자와 실제 앱 소유자** 두 관리 주체만으로도 충족할 수 있다. 팀 RBAC를 이유로 핵심 owner 기능을 뒤로 미루지 않는다.

## 5. 사용자 목록과 관측 데이터의 최소 계약

- 앱 관계: clientId+사용자ID, 최초 승인시각, 마지막 인증시각, 마지막 접근 관측시각, 앱 접근 상태, 해당 앱 차단/허가 만료. 각 값의 출처와 관측 지연을 구분.
- 로그인/토큰 발급은 실제 페이지 이용과 별개다. 게이트가 승인한 접근 관측을 비동기로 집계하며 보호 hot path에 중앙쓰기/원격조회 추가 금지.
- 제안: 앱-사용자-5분 구간당 대표 관측, isolate 내 중복 억제와 수신측 idempotency. 다중 isolate 때문에 실제 전송이 완전1회가 되는 것은 아니며 상한/비용을 측정한다.
- 관측 실패는 사용자 인증을 실패시키지 않는다. 목록에 최근 관측일 뿐 '실시간 온라인'이 아님을 표시. 인증/차단 판정의 권위 데이터로 telemetry를 사용하지 않는다.
- 익명 거부는 사용자ID 없는 이벤트/집계. 사전 허가로 입력한 ID는 '초대/사전등록'이며 방문한 사용자로 표시하지 않는다.
- owner에게 다른 앱 이력·중앙 관리자 토큰·전체 역할 목록·전역 제재 내부 사유는 노출하지 않는다. 자기 앱 운영에 필요한 표시명/식별 정보만 제공하고 조회도 감사 가능하게 한다.
- 개인정보 삭제와 보안 차단 tombstone은 별도: 사용자 목록에서 삭제했다고 기존 차단이 사라지거나 서비스 접근이 재허용되면 안 된다.

## 6. UI 설정의 최소 계약

`presentation`은 인증 policy와 별도 버전으로 관리한다. 임의 JavaScript/HTML 삽입을 기본 편집 기능으로 제공하지 않는다.

| 영역 | 제공할 설정 |
|---|---|
| 위젯 | visible/hidden, button/compact/menu, inline/fixed/sticky, 위치·여백·표시명 옵션 |
| 디자인 | light/dark/system 또는 검증된 색상·테두리·반경·크기 토큰 |
| 로그인 전 화면 | 서비스명, 로고, 제목/안내, 제한된 배경·레이아웃 프리셋 |
| 확인 중 화면 | 같은 브랜드/레이아웃, 진행 안내 문구, reduced-motion 지원 |
| 오류/거부/장애 화면 | 실제 사유에 맞는 설명·재시도·지원 링크; 거짓 성공 표현 금지 |
| 편집 수명 | draft → preview → publish → 이전 안전 버전 복원, version CAS |

hidden은 상시 위젯을 감추는 옵션이다. 서버 보호를 끄거나 필수 오류/복구 수단을 없애는 설정이 아니다. headless 사용자는 앱에서 제공할 로그인/로그아웃/복구 연결을 검사받는다. 필수가 아닌 '내 낙월 계정' 메뉴는 강제 노출하지 않는다.

fixed는 viewport 고정, sticky는 컨테이너 스크롤에 따른 고정으로 구분하고 모바일 safe area/키보드 focus/클릭 가림을 검사한다. 설정 화면에 정상·미로그인·확인 중·권한 거부·장애·모바일 상태 미리보기를 둔다.

로고·배경은 크기/MIME/URL 정책을 검증하고 비로그인에 필요한 최소 브랜드 자료만 공개한다. SVG/외부 URL/임의 CSS의 script·추적·정보 유출 위험을 처리한다. 사용자별 데이터나 비밀값을 공개 presentation endpoint에 넣지 않는다.

presentation 로딩 실패는 SDK의 안전한 기본 화면으로 복구하며 인증 판정은 그대로 유지한다. 설정은 매 이미지마다 조회하지 않는다. UI만 바꿨을 때 인증 lease나 사용자 세션을 무효화하지 않는다.

## 8. 개정판 재리뷰 합격 조건

1. owner A가 자기 서비스의 모든 필수 기능을 UI/API로 사용할 수 있고 B 서비스에는 접근/조치할 수 없다.
2. 앱 사용자 목록은 실제 관계·관측에 기반하며 익명 사용자의 신원을 만들어내지 않는다.
3. 앱 차단/세션 종료/기한부 허가와 중앙 조치는 분리되고 전파 지연이 표시된다.
4. 위젯/로그인/checking 편집과 초기 설치 미리보기가 실제 계획의 파일·스키마·테스트·릴리스 조건으로 내려온다.
5. UI 숨김·테마 오류·악성 입력으로 자료 접근이 열리지 않는다.
6. 정책은 owner에게 위임된 범위에서만 변경되고 기간 축소/확대가 약속한 방식으로 적용된다.
7. 늦은 refresh 응답·다중 isolate·동시 로그아웃/차단에서도 정상 사용자를 공격으로 오인하지 않고 세션이 부활하지 않는다.
8. 승인 근거별 만료 시험 네 가지가 명시된다.
9. 관측/설정 기능이 자산마다 중앙 통신을 추가하지 않는 성능 기준을 가진다.
10. 원본 보안·성능·호환성 조건과 새 외부 개발자 요구의 추적표가 완성된다.

위 조건을 개정판에 반영하기 전에는 두 문서를 외부 개발자용 상용 SDK의 완성된 개발 계획으로 승인하지 않는 것이 두 독립 리뷰의 공통 결론이다.
